  • retry()：失败后按 2 的幂次等待，再重新发起请求
  • jitter：在等待时间上加随机抖动，避免所有客户端同时重试
  • maxAttempts：给重试设上限，防止无限循环

重试的关键不是“再试一次”，而是“等多久再试”

最朴素的重试是失败后立刻再发一次。服务端过载时，这只会让压力翻倍。retry() 的做法是每次失败后把等待时间翻倍，并设一个上限。

注意第 6 行：等待时间是 base * 2 ** attempt，再乘以一个 0.5～1 之间的随机数。

export async function retry<T>(fn: () => Promise<T>, maxAttempts = 5, base = 200): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();
    } catch (err) {
      const wait = base * 2 ** attempt * (0.5 + Math.random() / 2);
      if (attempt + 1 >= maxAttempts) throw err;
      await new Promise((r) => setTimeout(r, wait));
    }
  }
}

只对幂等请求重试。POST 下单这类请求要先带上幂等键，否则重试会重复下单。

让模型遵守同样的规则

如果重试逻辑由 Agent 驱动，可以把规则直接写进系统提示词。下面是一段示例 Prompt：

# Retry policy

When a tool call fails with a 5xx or timeout:
1. Wait before retrying; double the wait each time (200ms, 400ms, 800ms…).
2. Stop after 5 attempts and report the last error to the user.
3. Never retry a non-idempotent call unless it carries an idempotency key.

退避时间线：抖动让重试错开

没有抖动时，同一时刻失败的客户端会在同一时刻重试，形成一波又一波的尖峰。加上抖动后，重试被打散到一个时间窗口里。

三种重试策略对比

策略等待时间适用场景
立即重试0偶发的网络抖动，且请求极便宜
固定间隔base轮询外部状态，例如等待 CI 结束
指数退避 + 抖动base * 2^n * rand服务端过载、限流（默认选择）
